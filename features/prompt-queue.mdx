提示词排队让你在 agent 还在跑的时候把后续要求写进去。
v1 有一堆联调暴露的问题，v2 把它们一次收干净——
这一页讲的是 v2 的设计，因为它正好能说明扣瓦怎么处理「前端状态」这类问题。

## v1 的病根

联调暴露的问题，多数指向同一类根源：
**队列状态没有持久化、事实源分散、前端对消息数组做多路手术**。

| 症状 | 根源 |
| --- | --- |
| 刷新 / 重启后排队消息失踪，排队条变成 ghost | 队列纯内存，sidecar 和前端镜像都是 |
| 消息数组要摘除 / 回填 / 恢复 / 抑制四条路径，还有恢复竞态、对账重复追加、顺序错乱 | 乐观消息直接在 Chat 数组里，与框架的重复项行为对抗 |
| 任意旁路流结束把会话状态打回 ready，按钮闪烁 | 框架 status 是单槽，旁路流生命周期各管各的 |
| 某轮失败后，后续排队项逐个撞同样的错误 | 没有熔断 |

## v2 的答案：快照，不是增量

<Columns cols={2}>
  <Column title="sidecar 侧">
    队列重写为纯状态机 `QueueEngine`——队列、自增 id、派发收口在一个无 I/O 的类里。
    **每次变更**向会话转录追加一行全量快照（`queue_state`），
    重启、切线程、树导航之后从最后一条恢复。
    同时向线程广播全量快照，前端「最后快照胜出」。
  </Column>
  <Column title="前端侧">
    store 变成**快照镜像**：全量替换，无增量对账。
    消息数组的同步规则从「四条路径 + 多个竞态补偿」收敛成**三条幂等规则**，
    组件挂载时按当前快照应用一次即完成对账。
  </Column>
</Columns>

选全量快照而不是增量的理由写在决策记录里：队列通常不超过 5 条，
全量最简单、没有对账逻辑，广播频率也低。

## 三条同步规则

前端对消息数组的所有操作收敛为三条，每条幂等：

| 规则 | 触发 | 做什么 |
| --- | --- | --- |
| R1 queued | 快照里有这条 | 消息只在排队条（从 Chat 数组摘除，防重复项） |
| R2 出队 | 快照里这条消失（轮真正开始） | 消息回填列表末尾；刷新后没有原气泡，就用快照文本重建 |
| R3 steered | 并入当前轮 | 维持「宿主轮收尾回填」——立即回填会在宿主轮写入窗口内触发重复项增长与乱序 |

被删掉的旧路径：restore 竞态补偿、cancelled 标记、对账方向分支——
全部由「快照状态 + 三条规则」替代。

## 四个操作

排队条上的操作只有四个，没有更多：

<CodeGroup>
```text 默认排队 / Queue
Enter 发送进队列，等当前轮结束按序派发。

立即发送 / Promote
插队，这条消息立刻派发。

并入当前轮 / Steer
不打断当前回合，但把这条消息交给正在跑的 agent。

删除 / Cancel
从队列里移除。
```
</CodeGroup>

编辑、暂停/恢复、熔断在重构中被**有意移除**：
派发中的项已从快照消失，无锁定态可言；
失败项随流终结回填成气泡，重发由你决定，而不是自动暂停闸。

## 附件不丢

早期快照只持久化文本，刷新后重建的气泡不带附件。
后来修掉了——快照条目现在携带图片附件
（协议形状 `{ name, mimeType, data | path }`，与 prompt 帧同形），
刷新/重启恢复、接力泵出队重发与队列条缩略图都不丢图。

<Note>
  有趣的坑：sidecar 原本按一个**前端从不发送**的 `type: "image"` 字段判形状，
  实际把图片全部丢弃。所以历史 queue_state 行无一携带附件。
  这类 bug 的教训是：协议形状要对齐已经在用的那一套，而不是发明一个新字段。
</Note>

## 「发送后、确认前」刷新

这是剩下的已知边界：注册表在前端内存里，刷新即清空。
此时那一项按快照重建（现在含图片附件），可接受。
