The prompt queue lets you line up follow-up requests while the agent is still working.
v1 accumulated a list of integration bugs; v2 cleared them in one pass. This page
describes v2's design, because it is a good illustration of how Kova handles frontend
state.

## What was wrong with v1

The bugs exposed during integration mostly pointed at the same roots: **queue state was
not persisted, the source of truth was scattered, and the frontend performed multi-path
surgery on the message array**.

| Symptom | Root cause |
| --- | --- |
| Queued messages vanished after refresh/restart; the queue bar became a ghost | The queue was purely in-memory — on both the sidecar and the frontend mirror |
| Message-array surgery needed four paths (remove / backfill / restore / suppress) plus restore races, duplicate-appends, and ordering bugs | Optimistic messages lived directly in the Chat array, fighting the framework's duplicate-entry behaviour |
| Any side stream finishing knocked the session status back to ready, flickering buttons | The framework's status is a single slot, and side streams each manage their own lifecycle |
| After one failed turn, every subsequent queued item hit the same error | No circuit breaker |

## The v2 answer: snapshots, not increments

<Columns cols={2}>
  <Column title="Sidecar side">
    The queue was rewritten as a pure state machine, `QueueEngine` — queue, auto-increment
    ids, and dispatch collapse into one I/O-free class. **On every change** it appends a
    full snapshot to the session transcript (`queue_state`); after a restart, a thread
    switch, or tree navigation it recovers from the last one. It also broadcasts the full
    snapshot to the thread, and the frontend adopts "last snapshot wins".
  </Column>
  <Column title="Frontend side">
    The store became a **snapshot mirror**: full replacement, no incremental
    reconciliation. The message-array rules collapsed from "four paths plus race
    compensations" into **three idempotent rules**, applied once on mount from the
    current snapshot — that alone completes reconciliation.
  </Column>
</Columns>

The reasoning for full snapshots over increments is in the decision log: queues are
typically ≤5 items, full replacement is the simplest thing with zero reconciliation
logic, and the broadcast rate is low.

## The three sync rules

Everything the frontend does to the message array reduces to three idempotent rules:

| Rule | Trigger | Action |
| --- | --- | --- |
| R1 queued | The item is in the snapshot | The message lives only in the queue bar (removed from the Chat array, preventing duplicates) |
| R2 dispatched | The item vanished from the snapshot (the turn truly began) | The message is backfilled at the end of the list; after a refresh there is no original bubble, so one is rebuilt from the snapshot text |
| R3 steered | Merged into the current turn | Keep "backfill when the host turn wraps" — backfilling immediately inside the host turn's write window triggers duplicate growth and reordering |

The deleted legacy paths: restore-race compensation, cancelled markers, reconciliation
direction branches — all replaced by "snapshot state + three rules".

## Four actions

The queue bar has exactly four operations, and nothing more:

<CodeGroup>
```text Queue (default)
Enter sends into the queue; dispatch happens in order after the current turn.

Promote
Jump the line — this message dispatches immediately.

Steer
Do not interrupt the current turn, but hand this message to the running agent.

Cancel
Remove it from the queue.
```
</CodeGroup>

Edit, pause/resume, and the circuit breaker were **deliberately removed** in the
refactor: a dispatching item has already left the snapshot, so there is no locked state
to render; failed items terminate with the stream and backfill as ordinary bubbles, and
resending is your call rather than an automatic pause gate.

## Attachments survive

Early snapshots persisted text only, so bubbles rebuilt after a refresh lost their
attachments. Fixed: snapshot entries now carry image attachments (protocol shape
`{ name, mimeType, data | path }`, same as prompt frames), so refresh/restart recovery,
pump redispatch, and queue-bar thumbnails all keep their images.

<Note>
  A bug worth remembering: the sidecar originally detected the shape by a
  `type: "image"` field that **the frontend never sent**, so it silently dropped every
  image — no historical `queue_state` row ever carried one. The lesson: align protocol
  shapes with what is already in use, do not invent a new field.
</Note>

## The known edge

Refresh between "sent" and "confirmed": the registry lives in frontend memory and is
cleared by the refresh, so the item is rebuilt from the snapshot (attachments included
now). Acceptable.
