Kova's extensibility comes in three layers: **tools** (what the agent can call),
**skills** (how the agent knows to do something), and **panels** (a UI a human can
open). A plugin can supply any combination of them.

## What a plugin is

**One directory plus one manifest** (`.kova-plugin/plugin.json`). The directory can hold
five kinds of components:

| Component | Manifest field | Purpose |
| --- | --- | --- |
| Skills | `skills` | Reusable methodology for the agent, triggered by `description` |
| MCP servers | `mcpServers` | A tool surface for the agent (external systems, analyses, …) |
| Panels | `panels` | Interactive UI in the right-side panel, bindable to workspace documents |
| Hooks | `hooks` | Commands run on agent lifecycle events (can block) |
| Subagents | `subagents` | Preset subagent definitions (invoked with `@`) |

## Where plugins come from: markets

Plugins do **not** live in the main repo; they are installed through markets. Add a
market in the app via "Plugins → Add marketplace", then install statements from it.
Two kinds:

<Columns cols={2}>
  <Column title="Directory market">
    Reads a local directory directly. Installation can be **linked** — the cache points
    at your source, so edits take effect immediately. Best for local development and
    private distribution.
  </Column>
  <Column title="Git market">
    Shallow-clones to the local disk; refreshing re-clones. Best for public distribution:
    push → refresh the market → update the plugin.
  </Column>
</Columns>

A market is "a directory containing `marketplace.json`" listing its plugins:

```json
{
  "name": "my-plugins",
  "displayName": "My plugins",
  "plugins": [
    { "name": "my-plugin", "source": "./plugins/my-plugin",
      "description": "One line about it", "category": "Productivity" }
  ]
}
```

After installation, a plugin is materialized into the app data directory
`plugins/cache/<marketplaceId>/<name>/` (a symlink to the source when installed linked).
A whole-package enabled switch controls all components; after install/uninstall/enable
changes, skills and subagents hot-reload, the MCP pool rebuilds, and panel lists update.

## The workspaces

The official plugin repository ships three workspaces through the market:

### Office

<Columns cols={2}>
  <Column title="Slides">
    Per-slide editing, presentation mode, and `.pptx` export. The agent collaborates on
    the deck through `<name>.deck.canvas.json`.
  </Column>
  <Column title="Spreadsheets">
    Powered by the Univer engine, with formulas, styles, merged cells, and frozen panes.
    The agent collaborates through `<name>.sheet.univer.json`.
  </Column>
</Columns>

### Canvas

An Excalidraw-style infinite space: text, shapes, images, Mermaid, tables, charts, and
embedded web pages placed freely, exportable as one SVG. The agent collaborates on
`<name>.canvas.json`.

### UI Design

A Figma-style page / artboard / layer tree plus a full property inspector. This plugin
goes one step further: it ships its own `.mcp.json` defining an MCP server, so the agent
can **drive the canvas directly through MCP tools** — add, edit, delete nodes, align,
distribute, stack, and group. It bundles three design-spec skills (iOS, Material, and
general mobile).

## How the agent uses plugins

The reason a plugin lets the agent actually do work — rather than hand you more
screenshots — is that **its output is structured data**.

<Columns cols={2}>
  <Column title="Editable output is the point">
    Canvas documents are `<name>.canvas.json`, slides are `.deck.canvas.json`,
    spreadsheets are `.sheet.univer.json`. The agent edits those JSON documents and the UI
    renders them — so it can add a shape or change a cell style instead of redrawing a
    picture for you.
  </Column>
  <Column title="Humans see it, agents get data">
    You open the panel to review and tweak; the agent keeps working on the same JSON.
    Both sides see different views of the same document, with no screenshot ping-pong.
  </Column>
</Columns>

Each of the three layers has its own trigger:

<CodeGroup>
```text Tool
Appears directly in the tool table; the model calls it like `read`.

Skill
Loaded on demand into context via `use_skill` rather than always resident —
otherwise every turn would carry three sets of design specs.

Panel
The agent can open a panel itself via `open_plugin_panel` and put the result in front of you.
```
</CodeGroup>

<Note>
  MCP tools are **not** registered as individual tools in the model tool table (that would
  break prompt prefix caching). They are called through a resident `mcp` gateway with the
  full name convention `<server>__<tool>`. So plugin skills should spell out the full name
  and the JSON-string `args` form instead of a bare tool name.
</Note>

## Skills

A skill is a knowledge pack loaded into the agent's context: no code, just "when this kind
of task comes up, follow these steps". Each skill is a `SKILL.md` whose `name` and
`description` are required — `description` decides **when it triggers**, so write trigger
scenarios, not a feature list. Skills are managed in Settings → Skills, and plugins can
contribute them via the manifest's `skills` field.

## Panels

Panels are interactive HTML contributed to the right-side panel. The host mounts them in
an iframe and talks over a postMessage bridge (`kova-ui-plugin/1`), so a panel can read and
write the workspace document bound to it.

Four entry points, all the same tab:

1. The panel list in the right panel's "+" menu;
2. "Open in panel" on a file artifact card (matched by the `opens` glob);
3. The agent calling the `open_plugin_panel` tool;
4. **Auto-open on first write**: the first time the agent's `write`/`edit` hits a panel's
   `opens` glob, the host opens that panel and binds the file.

<Warning>
  Panels run in an opaque-origin sandbox (`blob:` URL): `localStorage` / `cookie` are
  unavailable, relative-path assets do not load, all CSS/JS must be inlined, and the
  entry file is capped at 32 MiB. Panels must declare permissions
  (`document` / `export` / `agent` / `notify`); messages using undeclared capabilities are
  dropped.
</Warning>

## Distribution

The old mechanism that bundled plugin packages inside the app is gone: plugins are always
installed through a market — directory markets for local development and private
distribution, git markets for public distribution. Installation copies the plugin directory
(or links it to the source); source is the artifact, so no packaging chain is needed.

## Trust boundary

Installing a plugin that ships an MCP server = running its code with your permissions on
your machine. The host only accepts standard MCP fields, and tool calls still go through
the [approval levels](/en/features/modes) and approval policy. Try plugins in an isolated
directory first; do not install unknown third-party plugins into a production setup.
